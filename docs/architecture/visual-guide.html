Angular WebMCP Architecture

WebMCP lets a page hand an AI agent typed, callable functions instead of making it guess at your UI. Angular adds two things to that — a tool's lifetime and its injection context — in about 25 lines. This is how the pieces fit, and where they bite.

01

The shift: from guessing pixels to calling functions

Before WebMCP, an agent driving a web app had one option — pretend to be a person. Screenshot the page, guess which pixels are a button, click, screenshot again.

The entire browser surface is three members on one object:

document.modelContext.registerTool(tool, {signal?, exposedTo?})  // Promise<void>
document.modelContext.getTools({fromOrigins?})                   // Promise<RegisteredTool[]>
document.modelContext.ontoolchange                               // event handler
Misconception

WebMCP is not JSON-RPC. The W3C draft has no wire format at all — it is a direct in-page JavaScript API, and the intended consumer is the browser's own agent. JSON-RPC enters only when you want to reach an agent outside the page, which is a separate, non-standard layer (§06).

Three layers, and what each one owes you

03

The lifecycle: there is no unregisterTool

This is the idea everything else rests on. Look at the interface again — there is no method to remove a tool. So how does one ever go away?

Through the AbortSignal you passed when registering it. Aborting that signal is unregistration. That is the entire removal mechanism — and it happens to be the exact shape of Angular's DestroyRef.

Everything else — providers, scopes, route behaviour — is a consequence of which injector you attach to.

The two registration doors

// app.config.ts — lives as long as the root injector
providers: [ provideExperimentalWebMcpTools([getBoardTool]) ]

// a component or service — lives as long as that instance
constructor() {
  declareExperimentalWebMcpTool({ name: 'add_note', … });
}
Silent failure

provideExperimentalWebMcpTools does not await its registrations. registerTool rejects with InvalidStateError on a duplicate name, so a collision becomes an unhandled promise rejection — bootstrap succeeds and the second tool is simply absent. If you see a stray InvalidStateError and the app otherwise works, that is it.

04

Anatomy of a tool call

Two details the docs once got wrong

  • execute takes a second parameter. client.signal is an AbortSignal — pass it to any fetch so a cancelled turn actually cancels the work.
  • It returns unknown, not a {content: […]} envelope. There is no WebMcpToolResult type in Angular. Return a string; the browser serializes it.
Nobody validates

Not the spec, not the browser, not Angular. inputSchema is a hint to the model, not a runtime guard — an agent can send {square: 99} for a field you declared maximum: 8. So validate, and return the problem as text. A thrown exception ends the turn; a described failure lets the agent correct itself: 

agent → make_move({square: 4, player: "O"})
      ← "Move rejected. Square 4 is already taken by X.
         Empty squares are: 0, 1, 2, 3, 5, 6, 7, 8."
agent → make_move({square: 5, player: "O"})    ← it fixed itself

Good error text is not politeness here. It is the control flow.

05

Scope: the agent should see what applies here, now

It is tempting to register everything at the root. Two reasons not to. Every tool's name, description and schema is sent to the model on every turn — fifty always-on tools is a permanent token bill. And a model choosing between six relevant tools does better than one choosing between fifty, most of which cannot apply.

What to do

Declare page-scoped tools in the routed component. The router already creates and destroys that component, so its lifetime is the route's lifetime — on every version. On Angular 22 you may instead use provideRouter(routes, withExperimentalAutoCleanupInjectors()), which cannot be backported because its RouterFeatureKind is a v22 enum value.

The general move: find the thing whose lifetime you actually mean, and attach there. A tool that should exist only while a dialog is open belongs in the dialog's constructor. If nothing has the lifetime you want, create an injector that does.

06

Getting tools out of the page

Every diagram so far has put the agent inside the browser — which is what the W3C draft is designed for. But most agents people actually use live outside it.

The polyfill must win the race

Native WebMCP is Chrome-only and flagged, so in practice you develop against a polyfill. It has to finish before tools register — which rules out doing it in a provider, because provideExperimentalWebMcpTools registers from an environment initializer during bootstrap: 

installWebMcpPolyfill()
  .then(() => bootstrapApplication(App, appConfig))
  .catch(err => console.error(err));

// a .then chain, not top-level await — Angular's default browserslist
// targets reject it and the build fails outright

A convention worth copying from MCP

Over the bridge, a tool that fails returns a successful response with isError: true — not a JSON-RPC error. Same reasoning as §04: the model is meant to read the failure and adapt. Protocol errors are reserved for protocol problems: unknown method, malformed request, no such tool.

07

What bites you

Nine things measured the hard way. None of them announce themselves — the failure mode for most is silence.

01

Nothing validates the agent's arguments

A tool receives {square: 99} for a field declared maximum: 8.

Fix Validate in execute; return the problem as text.

02

Duplicate names are an unhandled rejection, not a throw

A stray InvalidStateError, the app works, one tool is missing.

Fix Namespace names — they are unique per document, not per module. Watch for a component rendering twice at once.

03

Route-level providers leak before Angular 22

Tools from a page you left are still in the list.

Fix Declare in the routed component instead.

04

executeTool is not standard

executeTool is not a function — usually in an in-page chat or inspector.

Fix Feature-detect it. The polyfill supplies it; the bare spec does not.

05

inputSchema comes back in two shapes

A JSON string on Chrome 149–153, an object from 154.0.8013 onward.

Fix Branch on typeof and guard the parse. Affects reading tools back, not registering them.

06

title defaults to ''

Blank labels in a tool list — ?? only falls through on null/undefined.

Fix tool.title || tool.name

07

file: installs break secondary entry points

TS7031: implicitly has an 'any' type on tool arguments, with nothing pointing at the cause. A symlink defeats the self-referential type import, and skipLibCheck hides it.

Fix Test against a packed tarball, which installs as a real directory.

08

toolchange does not fire where the spec says

The spec dispatches on the document. The polyfill dispatches only on the ModelContext. Measured across route changes: document listener 0 calls, context listener 4.

Fix Listen on both.

09

Heterogeneous schemas will not type-check in one array

One type parameter covers the whole array, so tools with different schemas have no valid S — angular#70125, still open.

Fix One provideExperimentalWebMcpTools call per tool; each array stays homogeneous and needs no cast.

The wider lesson · from pitfall 08

That bug survived twenty passing tests, because the test fake dispatched toolchange on both targets — faithful to the spec, and therefore more generous than the real implementation. A fake more capable than reality hides exactly this class of bug.

Anything that depends on where an event fires, or on event.origin / event.source, cannot be trusted from jsdom. Only the browser could have caught it.

A debugging checklist

  1. Is it registered? await document.modelContext.getTools() in the console.
  2. If not — did registration throw? Is document.modelContext even there? Is this a server render?
  3. Did it vanish? Something destroyed its injector. Which one did you attach to?
  4. Is it there twice? A component rendering twice, or two features choosing one name.
  5. Does calling it throw NG0203? Something is calling execute directly instead of going through executeTool, skipping runInInjectionContext.
  6. Does the agent keep misusing it? That is a description problem, not a code problem.
